# Decision Making generator

Read the current brief, full corpus inventory, nearest matches, content spec, and JSON contract. Write a versioned candidate plus manifest; never overwrite preview JSON or create SQL.

Plan each problem by reasoning mechanism before prose: premises and quantifiers, constraint model, dataset/table operations, argument criterion, Venn topology/region sums, or probability mechanism. Record a semantic fingerprint and nearest existing content. Changing names or numbers is not novelty.

Before writing Venn items, make a batch grid of format (diagram selection or stimulus interpretation), set count, shape palette, region topology, and reasoning task. Meet the brief's Venn mix constraints across the batch. Use the selected answer diagram when counting shapes and topology for a diagram-selection item; all four diagram options still need valid, renderer-supported configurations with the same set labels and shapes because the app shows one shared key. Do not produce a batch of repeated circle-only numerical lookups. Record the planned mix and the realised mix in the manifest.

For each new Venn configuration, bake every stimulus and option diagram at natural size and at narrow phone widths. Check that the visible overlaps match the declared regions, including zero-count regions; a successful bake alone does not detect an unlabelled overlap. Confirm the key identifies each shape unambiguously, especially when a shape repeats.

For varied heights, proportions and angles, use the v2 explicit-geometry format. Run `npm run questions:venn:generate` for seeded proposals, or author the set geometry and call `createVennFromGeometry()`. The engine derives every connected face before counts are assigned and rejects unreadable slivers. Keep its full region list, including zeros and disconnected pieces. Use `evaluateVennQuery()` to record exact sums and `vennFingerprints()` to distinguish topology from cosmetic pose changes. Inspect the generated HTML gallery at phone widths. These diagrams and computed sums are authoring inputs; they still need question prose, plausible distractors, corpus novelty screening and independent blind validation. Do not randomise geometry when displaying a saved question.

Use `generateVennBatch()` or CLI `--count` for broader variety: the proposal grammar combines 16 layout families with continuous geometry changes, and the batch balances families while requiring different canonical overlap structures. Save the full generated config, including `labelStyle` (default 14 px minimum, 18 px preferred, 3 px padding). Inspect `diagnostics.regionSpace` and the gallery's label-space overlay; every padded label rectangle must fit within its actual face. Plan variation in overlap depth, containment/separation, disconnected faces and query operation, alongside shape palettes and rotation. Pass previous `topologySignature` values via `excludedTopologies` for structural screening across batches. Rotation, palette and set reordering do not count as a new overlap structure.

For each answer, solve before writing distractors. Distractors must correspond to distinct plausible errors. For five-statement questions, derive every answer separately and include a statement-specific explanation. For numerical and Venn work, record inputs, expression/region totals, unrounded result, rounding, units, and selected label in the manifest.

Practice question totals and type/difficulty allocations come from the brief. Full timed tests must meet the app's 35/37 contract and allocation described in the content spec.
